# 一、项目最终目标

我们不应该把 OpenShorts 简单改成“另一个 Opus Clip”。

真正目标应该是：

> **输入一个或多个 YouTube 长视频 URL + 用户提供的参考短视频脚本 → AI 自动理解长视频 → 从一部视频中发现多个独立故事 → 按参考脚本风格重新编写旁白 → 检查旁白与原始画面是否匹配 → 淘汰不合格脚本 → TTS → 自动剪辑 → 9:16 → 字幕 → 输出多个短视频。**

最终系统：

```text
YouTube URL
    │
    ▼
Source Analyzer
    │
    ├── 视频标题/描述/章节/元数据
    ├── YouTube字幕
    └── 视频源状态
    │
    ▼
Transcript Engine
    │
    ├── YouTube字幕优先
    └── Whisper兜底
    │
    ▼
Media Understanding
    │
    ├── Scene
    ├── Keyframe
    ├── OCR
    ├── 人物
    ├── 屏幕内容
    └── Audio/Event
    │
    ▼
Story Discovery Engine
    │
    ├── Story A
    ├── Story B
    ├── Story C
    ├── Story D
    └── ...
    │
    ▼
Reference Style Engine
    │
    ▼
Script Generation
    │
    ├── Script A1
    ├── Script A2
    └── Script A3
    │
    ▼
Video-Script Match Engine
    │
    ├── Visual Match
    ├── Temporal Match
    ├── Narrative Match
    ├── Fact Match
    └── Coverage
    │
    ├──────────── FAIL
    │               │
    │               ▼
    │          重新生成/淘汰
    │
    ▼ PASS
TTS
    │
    ▼
Timeline Builder
    │
    ▼
OpenShorts Reframe Engine
    │
    ▼
Subtitle / Hook / Layout
    │
    ▼
Final QC
    │
    ▼
15–35s / 9:16 MP4
```

# 五、最重要的架构升级：字幕优先

## 当前 OpenShorts

```text

 ↓

 ↓
```

# 六、改成 Analysis-First

新系统：

```text
YouTube URL
    │
    ▼

    │
    ▼
Subtitle Fetch
    │
    ├── 人工字幕
    ├── 自动字幕
    └── 无字幕
```

所以：

### 有 YouTube 字幕

完全不运行 Whisper。

### 没字幕

才运行 Whisper。

# 八、字幕优先级

推荐：

```text
Priority 1
用户指定字幕语言

Priority 2
视频主语言人工字幕

Priority 3
视频主语言自动字幕

Priority 4
英语人工字幕

Priority 5
英语自动字幕

Priority 6
Whisper
```

不能简单：

```text
--sub-langs all
```

因为语言太多会浪费时间。

先读取字幕轨信息，再选目标语言。

# 九、字幕质量检查

不能拿到字幕就直接相信。

必须检查：

### 1. 时间覆盖率

例如：

```text
视频 3600s
字幕覆盖 3510s
```

覆盖率：

```text
97.5%
```

可以。

---

### 2. 字幕密度

例如：

```text
每分钟平均字符数
```

如果：

```text
3600秒
只有300个字
```

明显不正常。

---

### 3. 时间轴合法性

检查：

```text
start >= 0
end > start
end <= video_duration
```

---

### 4. 重复字幕

YouTube VTT可能存在重复/滚动字幕。

统一：

```text
normalize_subtitle()
dedupe_subtitle()
merge_adjacent_subtitle()
```


# 十一、一个非常重要的优化

## 不要对整部视频做 Whisper

即使 YouTube 没字幕。

应该：

```text
YouTube无字幕
    ↓
粗略故事发现
    ↓
找到候选区域
    ↓
只对候选区域 Whisper
```

如果必须全文：

才跑全文 Whisper。

因此系统有三个 Transcript Level：

```text
L1
YouTube Caption

L2
Segment Transcript

L3
Word-level Whisper
```

按需升级。

# 十二、Video Analysis也采用“延迟下载”

这是第二个非常重要的架构。

以前：

```text
YouTube
 ↓
下载完整视频
 ↓

```

我们改：

```text
YouTube
 ↓
字幕/元数据
 ↓
故事候选
 ↓
只获取候选需要的视觉信息
```

如果使用支持在线视频 URL 的视频理解模型：

```text
YouTube URL
 ↓
Video Understanding API
```

直接分析。

如果模型不支持：

```text
YouTube
 ↓
下载低分辨率代理/候选片段
 ↓
视觉分析
```

最后只有通过质量门禁的候选才需要进入完整渲染。

# 二十、故事去重必须比 OpenShorts 原版更强

OpenShorts原版主要解决：

> 时间区间重叠

我们的系统还必须解决：

> **语义重复。**

例如：

```text
Story A:
“男子发现汽车故障”

Story B:
“汽车突然出现故障”

Story C:
“男子解决汽车故障”
```

实际上可能是同一个事件。

所以需要：

```text
Temporal overlap
+
Semantic similarity
+
Character overlap
+
Scene overlap
+
Event overlap
```

综合判断。

# 三十一、Visual Alignment

判断：

> 旁白说的东西，画面有没有？

例如：

旁白：

> “男人拿起了桌上的钥匙。”

画面：

```text
男人
+
桌子
+
钥匙
+
拿起动作
```

高分。

---

如果画面只有：

```text
男人站着
```

低分。

---

# 三十二、Temporal Alignment

最容易被忽略。

例如：

旁白：

```text
“接下来，他打开了门。”
```

但画面：

```text
打开门
发生在后面5秒
```

那么：

```text
Temporal mismatch
```

必须检查。

---

# 三十三、Fact Alignment

旁白：

> “这是他第一次来到这里。”

如果原始视频没有证据。

不能通过。

因为这是：

```text
AI hallucination
```

必须：

```text
UNSUPPORTED FACT
```

---

# 三十四、Narrative Alignment

判断：

> AI有没有改变原故事因果关系。

例如原视频：

```text
A发现问题
→
B解释
→
A解决
```

脚本不能写成：

```text
A发现问题
→
A自己解决
```

即使画面“看起来像”，也不行。

---

# 三十五、Evidence Types

统一：

```text
TRANSCRIPT
VISUAL
OCR
TEMPORAL
AUDIO
METADATA
INFERENCE
```

其中：

```text
INFERENCE
```

默认不能作为关键事实证据。

# 三十六、Match Score

推荐：

```text
MatchScore =

0.25 * Visual
+
0.20 * Temporal
+
0.20 * Fact
+
0.15 * Narrative
+
0.10 * Coverage
+
0.10 * Style
```

然后设置硬门槛：

```text
Visual >= 0.75
Fact >= 0.90
Temporal >= 0.80
Narrative >= 0.80
```

即使总分很高：

```text
Fact = 0.55
```

也：

```text
FAIL
```

---

# 三十七、为什么必须设置“硬门槛”

因为：

```text
视觉漂亮
+
文案非常好
+
Hook非常强
```

不能掩盖：

> **事实是假的。**

```text

 ↓

 ↓

 ↓

 ↓

 ↓

 ↓

 ↓

```

# 三十九、Claim Extraction

例如：

> “女孩看到门后站着一个男人。”

拆成：

```text
Claim 1:
主体 = 女孩
```

# 一百零八、最终产品和原 OpenShorts 的区别

OpenShorts：

```text
长视频
 ↓
精彩片段
 ↓
Short
```

我们最终：

```text
长视频
 ↓
理解整部视频
 ↓
发现多个完整故事
 ↓
分析参考脚本风格
 ↓
重新编剧
 ↓
验证每句话是否有视频证据
 ↓
验证时间关系
 ↓
验证事实
 ↓
淘汰错误脚本
 ↓
TTS
 ↓
智能重构画面
 ↓
Short
```

这已经不是简单的：

> **AI自动剪辑工具**

而是：

> **AI短视频编导系统。**

---

# 一百零九、我认为这个方案里最重要的三个技术决策

### 第一

**YouTube字幕优先，Whisper兜底。**

直接解决现在最明显的速度瓶颈。

---

### 第二

**故事和片段彻底分开。**

OpenShorts找的是：

```text
moment
```

我们找的是：

```text
story
```

这是产品核心差异。

---

### 第三

**Match Engine必须在TTS之前。**

顺序永远：

```text
Story
→ Script
→ Evidence
→ Match
→ PASS
→ TTS
```

而不是：

```text
Story
→ Script
→ TTS
→ Render
→ 才发现脚本和画面不一致
```

---

# 一百一十、最终建议

我现在对 OpenShorts 的判断已经和最开始不同：

**它不是一个需要“大改才能用”的垃圾底座。**

恰恰相反：

> **它的视频工程部分已经非常成熟，真正欠缺的是“内容理解层”。**

目前仓库已经有成熟的：

```text
下载
转录
场景
AI选片
视觉分析
人物跟踪
9:16
字幕
Hook
FFmpeg
任务
API
MCP
CLI
```

甚至已经有视觉 Clip Selection、Grounded Hook、布局选择等能力。([GitHub][4])

所以最合理的研发策略不是：

> “重新开发一个 AI 视频生成软件。”

而是：

> **把 OpenShorts 当作 Video Production Engine，在它上面增加 Story Intelligence Layer。**

最终形成：

```text
                 OpenShorts
              Video Production
                     +
              ┌─────────────┐
              │ Story Engine│
              ├─────────────┤
              │ Style Engine│
              ├─────────────┤
              │Script Engine│
              ├─────────────┤
              │ Match Engine│
              └─────────────┘
                     ↓
              AI Short Factory
```

**这条路线是我认为目前开发量、技术风险、最终效果三者之间最优的方案。**

尤其是第一步，我建议马上改成：

```text
YouTube URL
 ↓
获取字幕
 ↓
如果有字幕：
    完全跳过 Whisper
 ↓
Story Discovery
```

因为当前 OpenShorts 的默认核心链路确实仍把 `faster-whisper` 放在分析前面，而仓库本身的转录后端已经为我们提供了非常好的替换接口。([GitHub][1])

**下一阶段真正应该进入“代码级设计”：我建议直接按照这份文档，把当前 OpenShorts 的文件逐个标成 `保留 / 修改 / 拆分 / 新增`，然后给出每个文件具体改什么、函数级接口怎么定义、JSON Schema 怎么定义、任务状态怎么流转。这样下一步就可以直接开始改代码，而不是再讨论概念。**

补充一点：我这次重点审查的是**当前 `main` 分支中与这次改造直接相关的完整后端/AI/媒体处理链路和仓库工程结构**；仓库还有 dashboard、cloud、Remotion、部署、营销页面等大量与核心算法无关的前端/运营代码，我没有把每一个前端组件逐行复述，因为它们不会改变这套核心改造架构。当前仓库的目录结构和核心文件可以直接在官方仓库看到。([GitHub][1])
